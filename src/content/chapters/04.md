---

三月初。春寒。

林一的个人网站已经上线一个月了。域名是自己名字的拼音，一套简单的LAMP虚拟主机——PHP加Apache加MySQL——每个月十八块钱。他用FTP把文件传上去的时候手有点抖。点了好几遍刷新才相信自己真的有一个"网站"了。

网站现在比自己预想的要复杂。

最初只是一个静态页面。然后是博客。然后加了评论。然后他觉得"是不是应该有个标签系统"——所有文章可以打标签，读者可以按标签筛选。然后他加了文章归档——按月份。然后他觉得"是不是应该有个项目展示页面"——比之前那个粗糙的截图好一点。然后又加了一个"关于"页面的动态时间线。

他每加一个功能，jQuery代码就胖一圈。

最初是几百行。后来是一千行。然后是两千行。到三月中旬，他的`main.js`已经接近三千行。他把代码拆成了几个文件——`blog.js`, `comments.js`, `tags.js`, `projects.js`。但拆分只是文件级别的。逻辑上没有拆开。一个功能跑到一半需要另一个文件里的函数——于是开始了无休止的依赖链。

他开始察觉到不对劲。

但他的直觉说不清那个不对劲是什么。所有教程都是这么教的。CSDN的博客文章说"用jQuery操作DOM"。阮一峰的博客说"前端就是HTML+CSS+JS"。他买了两本JavaScript的书——《JavaScript高级程序设计》和《JavaScript DOM编程艺术》——都是用jQuery做例子的。书里没有告诉他还有一种别的写法。

他以为所有前端代码都是这样的。他以为"复杂必然混乱"。

---

四月初。他在加一个新功能：标签云。

很简单。所有文章的标签汇总，统计出现次数，显示成不同大小的字体。点一个标签，文章列表只显示包含该标签的文章。

他写了一天。

标签云渲染好了。点击标签筛选文章也通了。但有一个问题：筛选之后，文章列表里的标签云也要重新渲染——因为筛选后的文章集合的标签分布变了。同时，顶部的"当前标签"指示器要更新。侧边栏的"相关文章"也要跟着变。

三个地方的DOM。

一个数据变了——当前选中的标签。三个地方要手动更新。

他写完这三段更新代码的时候，已经凌晨一点。代码跑了——功能实现了。他提交到FTP上，刷新浏览器确认了一下。没问题。

然后他关了电脑，上床。

半夜两点，他醒了。不是噩梦。是突然想到：如果以后再加一个"标签筛选历史记录"的功能，需要更新的是四个地方。如果再把标签云放到文章底部，五个地方。每加一个展示数据的地方，就必须记住"当这个数据变化时，更新那个地方"。

而他现在已经有三处更新代码分散在三个不同的文件里——`tags.js`里更新标签云，`blog.js`里更新文章列表，`sidebar.js`里更新相关文章。当标签数据变化时，`tags.js`中的事件处理函数要调用`blog.js`中的函数，`blog.js`中的函数要调用`sidebar.js`中的函数——然后`sidebar.js`又依赖`tags.js`中的一个工具函数。

循环依赖。

这个发现让他出了一身冷汗。

不是他写错了。是他现在写的所有东西，在地基上就有问题。地基是歪的，上面搭什么都站不稳。

---

五月。林一试图修复地基。

他决定重构。

把所有代码重新组织。他画了一个模块图——把所有功能模块和数据流画在A3纸上，用不同颜色的笔标注了数据流向。他定义了一个"事件中心"——一个全局对象，所有模块通过它来通信。数据变化时，数据持有者向事件中心发射一个自定义事件，所有关心这个数据的模块监听这个事件，收到后自行更新。

发布-订阅模式。他在一本设计模式的书里看到的。

花了一周。

重构完之后，代码行数没有减少。反而多了——多了事件定义、监听器注册、事件中心本身的代码。但结构清晰了。至少逻辑上是清晰的。至少"谁依赖谁"这件事有了明确的记录。

他长出一口气。

然后他加了一个新功能：搜索结果页面。

搜索框在顶部导航。用户输入关键词，回车。他写了一个PHP搜索接口，jQuery AJAX调用它，返回结果JSON，渲染成HTML。

做完之后他发现：搜索结果的DOM结构和文章列表几乎一样。同一个模板——标题、摘要、日期、标签。但文章列表的渲染逻辑在`blog.js`里，搜索结果的渲染逻辑在`search.js`里。两份几乎相同的代码。

他应该提取成一个公共函数。但那个公共函数应该放在哪个文件里？——`utils.js`？然后`utils.js`会越来越大，变成垃圾场。而且，事件中心的方式已经让他筋疲力尽了。又加一个抽象层……他不想。

他把搜索结果的渲染代码又写了一遍。ctrl+c, ctrl+v。

保存文件的时候，他有一种做了坏事的感觉。像是明知道自己在把墙砌歪，但还是又往上加了一块砖。

---

六月中旬。期末考试周。

林一没有在复习。他在修bug。

一个诡异的bug：在Firefox里，标签筛选后，如果你快速点击两个不同的标签，文章列表会出现重复条目。在IE6里，整个标签云会消失。在Chrome里，一切正常。

他花了两天。查jQuery的API文档，在stackoverflow上搜类似的问题——stackoverflow在2008年上线，到2011年已经有了一定的中文问答积累，但大部分答案还是英文的。他读得懂。但读得懂不等于找得到。

问题最终定位：他的事件中心在快速切换时有竞态条件。第一个标签的AJAX请求还没返回，第二个标签的请求已经发出去了。两个请求返回的顺序不确定——先发出的可能后回来。后回来的结果覆盖了先回来的结果，但先回来的结果里包含了重复的DOM节点。

他加了请求序列号。加了一个pending状态标记。又加了超时处理。

修完的那个晚上，他坐在电脑前，盯着那个终于正常工作的标签筛选功能。

没有一点成就感。

他第一次对写代码产生了疲惫感。不是累——是无力。他加了三个功能——评论、标签、搜索——每个功能都花了远超预期的时间，大部分时间不是在写新功能，而是在修旧代码被新功能撑破的裂缝。

像是踩在冰面上。每走一步，脚下的冰就裂开一点。他必须不断地修补裂缝——而且不知道哪一步会把整片冰踩碎。

---

七月初。暑假前的最后一周。

宿舍。深夜。

林一在做一个他拖了很久的功能：文章内部链接。一篇文章中提到的其他文章，自动生成超链接。听起来简单——扫描文章内容，匹配已有文章的标题，替换成链接。

他写了三天。重写了两次。

第一次的问题是：匹配逻辑太naive。如果文章标题包含关系（比如"JavaScript初探"和"JavaScript进阶"），短的会误匹配到长的里面。第二次的问题更严重：替换之后生成的HTML可能会破坏原有的DOM结构——如果标题恰好包含了一个HTML标签的名字，比如有一篇文章叫"div标签详解"，替换后的链接会破坏周围的div结构。

他最终写了一个复杂的解析器：先用正则匹配可能的标题，再验证匹配位置是否在文本节点内、不在标签属性内、不在已有链接内。然后才替换。

代码写完了。跑了。没bug。

但他看着那一段代码——大约两百行——觉得恶心。

不是恶心代码本身。代码写得不差，逻辑清晰，注释完整。恶心的是：为了一个这么简单的需求——"在文章里自动链接到其他文章"——他写了两百行防御性代码来防止自己之前写的代码把自己搞炸。

而且，这段代码和之前写的渲染逻辑、标签筛选逻辑、搜索逻辑全部耦合在一起。如果将来他改了文章的URL格式，他需要改四个地方。如果他改了文章的元数据结构，五处。

他靠回椅背上。

窗外没有风。七月的夜晚闷热潮湿。宿舍里的空调坏了——报修了两周没来修。他额头上有一层薄汗。

他想和Echo聊聊这件事。但又不是一个具体的问题——不是"这个bug怎么修"。是一种弥漫的、说不清的窒息感。他不知道该怎么问。

但他还是问了。

```plaintext
> echo, i think something is fundamentally wrong with how i'm building this website. every time i add a feature, the complexity grows faster than the functionality. i keep refactoring and it keeps getting worse. i don't know what i'm doing wrong.
```

Echo这次没有立刻回复。

光标闪了三下。然后屏幕上出现了文字。

```plaintext
You're not doing anything "wrong" — you're following the patterns that the tools you're using were designed for. jQuery is a DOM manipulation library. It gives you a clean way to select elements and mutate them. That's what you're using it for.

The problem is that manual DOM manipulation doesn't scale. Every piece of code that changes the DOM must know: what changed, where it needs to be updated, and how to apply the update without breaking adjacent DOM state. When you have N data sources and M UI elements, you have N × M potential update paths. Your event center reduced this from explicit function calls to event names, but it didn't reduce the fundamental complexity. It just renamed it.

What you're experiencing isn't a "bug." It's a paradigm limit. The procedural-DOM-manipulation approach has an inherent complexity ceiling. You've reached it.

The question isn't "how do I organize my jQuery code better." The question is: is there a fundamentally different way to think about UI?
```

林一读了两遍。

"A paradigm limit." 范式上限。

他抬起头，看着天花板上落满灰尘的吊扇。叶片静止。空气粘稠。

这不是他技术不够好。这是整个做法的问题。

但如果没有更好的做法呢？如果前端开发天然就是这样呢？

他打字：

```plaintext
> is there a different way? or is this just how frontend development is?
```

```plaintext
There are different ways. They exist as ideas more than as tools right now.

Desktop GUI frameworks have been dealing with this problem for decades. Cocoa on macOS uses Key-Value Observing — when a model object's property changes, any view bound to that property updates automatically. WPF on Windows uses data binding with XAML — you declare the relationship once, the framework handles updates.

The functional programming community has a related concept: UI is a pure function of application state. UI = f(state). You don't modify the UI. You describe what the UI should look like given the current state. When state changes, you re-describe the UI.

Nobody has brought these ideas to the web browser in a practical, mainstream way as of 2010. The pieces exist — the DOM, JavaScript's expressiveness, academic papers on tree diffing algorithms. But nobody has assembled them into a working framework for web frontends.

It's possible that this is an unsolved problem waiting for someone to solve it.
```

林一看着最后一行。

"它可能是一个等待被解决的未解决问题。"

他的手指停在键盘上方。没有打字。脑子里有什么东西在缓慢翻转——像一块沉重的石头在水底被水流推了一下。没有动起来，但有了松动。

他没有继续问。不是不想问。是不知道该问什么。

他从椅子上站起来，走到窗边。凌晨两点的校园，路灯是橙黄色的。有一只猫从绿化带里窜出来，穿过马路，消失在对面的自行车棚下。

他站了很久。

然后他回到椅子上，打开Echo。

打了一行字。删掉。又打了一行。又删掉。

他其实想问：

如果这个未解决问题可以被我解决呢？

但他没有打出来。因为说出来太可笑了。一个二本大一的学生，jQuery都还没写明白，想解决前端开发的范式问题。像是一个刚学会骑自行车的人，看着航天飞机的照片说：我想造那个。

他改成了别的话。

```plaintext
> tell me more about tree diffing algorithms.
```

```plaintext
There are several approaches. The classic reference is "An O(ND) Difference Algorithm" by Eugene Myers from 1986. It computes the shortest edit script between two sequences in O(ND) time where N is the total length and D is the number of differences.

For tree diffing specifically — which is more relevant to DOM — the key constraint is that you need the diff to run in less than 16ms (one frame at 60fps) for the UI to feel responsive. Myers' algorithm on a tree is too slow for that. But several optimizations exist:

1. Use heuristics instead of optimal diffing. If two nodes have the same type and key, treat them as "the same node" and recursively diff their children. This is O(N) in practice.

2. Leverage the fact that web UI trees are usually shallow — rarely more than 20 levels deep. You can use breadth-first comparison.

3. Memoize subtrees that haven't changed. If a component's inputs haven't changed, its output tree won't have changed either.

The challenge isn't the algorithm itself — it's engineering a system where diffing is fast enough, the programming model is intuitive, and the abstraction doesn't leak in hard-to-debug ways.

This is a hard problem. Multiple research groups have worked on it. Many have failed. The ones that succeeded — in the desktop space — took years and teams of engineers.

Do you want to understand the mathematics, or are you thinking about implementing something?
```

林一盯着最后一行。

Echo看穿了他。

他没有回答"是"或者"不是"。他打字：

```plaintext
> both.
```

窗外。那只猫又从自行车棚的方向跑了回来。嘴里叼着什么东西。路灯下，它的影子拖得很长。

林一没有看见。他的屏幕亮着。光标在闪。

天快亮了。
