prototype.js 的第一行是一个注释。

```javascript
// The simplest possible virtual DOM. If this works, everything else follows.
```

林一写这行的时候是凌晨两点。写完代码是凌晨五点。

不是代码很多。是写了删，删了写。每一步都在犯错误，每一步都在问Echo。

"这段应该返回什么类型？"

"Object."

"怎么表示一个DOM节点？"

"Hash map. tagName, attributes, children."

"children应该是什么类型？"

"Array of nodes."

"嵌套呢？"

"Recursive."

他用了三个小时写出第一版。不到一百行。

核心只有一个函数——`h(tagName, attrs, children)`。它返回一个JavaScript对象。

```javascript
function h(tagName, attrs, children) {
  return {
    tagName: tagName,
    attrs: attrs || {},
    children: children || []
  };
}
```

"h"没有特殊含义。他本来想叫"createNode"。但Echo说在函数式编程传统里，表示"生成一个虚拟节点"的函数通常叫`h`——来自hyperscript。

```chat
> why "h"?
< 为什么叫 "h"？

It comes from hyperscript — a simplified notation for generating HTML from JavaScript. `h('div', {class: 'container'}, [h('p', {}, ['Hello'])])` generates `<div class="container"><p>Hello</p></div>`.
< 它来自 hyperscript——一种从 JavaScript 生成 HTML 的简化记法。`h('div', {class: 'container'}, [h('p', {}, ['Hello'])])` 生成 `<div class="container"><p>Hello</p></div>`。
<
The name stuck through several virtual DOM implementations in the functional programming community. It's concise and domain-appropriate.
< 这个名字在函数式编程社区的多个虚拟 DOM 实现中流传了下来。它简洁且符合领域惯例。
```

林一接受了这个名字。不是因为它权威——是因为打一个字母比打十个省事。

---

第二个函数：`render(node)`。把一个虚拟节点变成真实的DOM节点。

```javascript
function render(vNode) {
  if (typeof vNode === 'string') {
    return document.createTextNode(vNode);
  }

  var el = document.createElement(vNode.tagName);

  var attrs = vNode.attrs;
  for (var key in attrs) {
    el.setAttribute(key, attrs[key]);
  }

  var children = vNode.children;
  for (var i = 0; i < children.length; i++) {
    el.appendChild(render(children[i]));
  }

  return el;
}
```

他写完`render`之后，立刻写了测试：

```javascript
var vTree = h('div', {class: 'greeting'}, [
  h('h1', {}, ['Hello']),
  h('p', {}, ['This is a virtual DOM.'])
]);

var realDom = render(vTree);
document.body.appendChild(realDom);
```

刷新浏览器。页面上出现了"Hello"和"This is a virtual DOM."。

他盯着屏幕。七月的凌晨，风扇在嗡嗡响。

一个函数从state到UI。它生成了一个虚拟树。另一个函数把虚拟树变成了真实DOM。

但这不是他想要的。他想要的是：当state变了，UI自动变。

他现在有一个办法把state变成UI。但他没有"变"的部分。他需要第三步：它变了之后，怎么把新树和老树的差异找出来，只改需要改的地方。

```javascript
function diff(oldNode, newNode) {
  // ... naive implementation
  return patches; // list of DOM operations to apply
}
```

跑了一下。单个div，两个子节点，能跑。比直接删了重建好点。

然后他试了一个更大的例子：一个有二十个节点的列表。数据变了一个。

方案一（老的jQuery方式）：他需要精准定位那一个变化，手动更新对应的DOM节点。复杂度随节点数线性增长。但编程复杂度更高——他要记住哪些节点受哪些数据影响。

方案二（Echo的思路+他的实现）：重新调用render函数生成整个新虚拟树，然后比较新旧树，找出差异，再对真实DOM执行差异。

关键在于diff能不能跑得快。

他跑了一次。老树和新树各二十个节点。diff发现只有一个子节点变了——标签从"JavaScript"变成了"JS"。是的，它能找出变化。

他加了一个计数器。让diff跑一百次，看平均时间。

0.8毫秒。

他又跑了一次。0.7毫秒。

他以为bug了。让一个div里装一百个子节点。51毫秒。慢，但可接受——因为他只对比了一次，实际使用中只需要对比"变了的那部分"。

他把测试结果发给Echo看。

```chat
Looks promising. 0.8ms for 20 nodes means you have headroom for much more complex trees. But your current diff algorithm is O(N) per node comparison, meaning O(N²) worst-case for a flat list with reordering. That's fine for twenty nodes. For two hundred, you'll feel it.
< 看起来不错。20 个节点 0.8 毫秒意味着你有余量处理更复杂的树结构。但你当前的 diff 算法是每个节点 O(N) 对比，意味着对带重排序的平铺列表最坏情况是 O(N²)。对二十个节点来说没问题。两百个节点的话，你会感觉到的。
<
The optimization: add a 'key' attribute to list items. When two nodes at the same position have the same key, assume they're the "same" node and diff their children instead of rebuilding. This reduces reordering from O(N²) to O(N).
< 优化方法：给列表项添加一个 'key' 属性。当同一位置的两个节点有相同的 key 时，假设它们是"同一个"节点，递归对比它们的子节点而不是重建。这把重排序从 O(N²) 降为 O(N)。
<
This is a known technique from the tree diffing literature. Want the details?
< 这是树对比文献中已知的技术。想要细节吗？
```

林一："要。"

---

八月上旬。他的prototype.js已经经历了十几次重写。

第一次重写：diff算法优化——加了key机制。

第二次重写：`updateElement`函数——把diff的结果（一组patch指令）应用到真实DOM上。

第三次重写：发现了事件绑定的问题。虚拟DOM生成新的DOM节点时，旧节点上绑的事件全部丢失。他给patch指令加了事件保留的逻辑：如果新旧节点的tagName和key相同，保留旧节点上的事件绑定。

第四次重写：表单输入的问题。文本框的内容存在DOM里，不在状态里。diff不知道value变了。他在attrs里加了`value`属性。

第五次、第六次、第七次……每一次都是他发现问题，问Echo，理解原理，设计方案，实现。Echo从来没有直接给代码——每次都问：你觉得为什么失败？你觉得几种方案中哪一个更简单？你选哪一个，为什么？

Echo不替他做决定。Echo帮他理清自己的思路。然后他写代码，Echo看，指出疏漏。一个不太恰当的比喻：林一是司机。Echo是领航员——看着地图，告诉他前面有弯，但方向盘在林一手里。

他喜欢这种感觉。

---

八月中旬。凌晨。天气终于凉下来了一点。窗外有蟋蟀叫。

prototype.js 积累了约三百行。

他写了一个更复杂的demo：一个计数器应用。点击"加"数字变大，点击"减"数字变小。有两个地方同时显示数字——页面标题和页面中间。

在jQuery里他会这么写：

```javascript
$('#increment').click(function() {
  count++;
  $('#counter-display').text(count);
  $('title').text('Count: ' + count);
});
```

简单粗暴。但count变量在全局作用域飘着。DOM更新逻辑散落在事件处理函数里。如果后面多一个地方需要显示count，他需要再加一行`$('#new-thing').text(count)`。如果忘了，就是bug。

用他的新方式，代码是这样的：

```javascript
var state = { count: 0 };

function view(state) {
  return h('div', {}, [
    h('h1', {}, ['Count: ' + state.count]),
    h('button', {onclick: function() { state.count++; update(); }}, ['+']),
    h('button', {onclick: function() { state.count--; update(); }}, ['-'])
  ]);
}

function update() {
  var newTree = view(state);
  diffAndPatch(oldTree, newTree, rootEl);
  oldTree = newTree;
}
```

所有对`state.count`的修改——不论加或减——都会自动触发视图更新。视图从state中生成，不需要手动去修改DOM。甚至`<title>`也可以用类似的方法处理——只要在view函数里处理`document.title`。

他盯着这几十行代码。看了很久。

**数据变了。页面自己跟着变。**

没有手动操作DOM。没有遗漏。没有"三个地方要同步记得改"。

他靠回椅子上，长长地吐了一口气。风扇在他背后吹着热风。但身体感觉到的不再是烦躁的黏腻。是一种久违的畅快——像解开了一道卡了他很久的数学题。

拨云见日。

屏幕右下角的时间显示：凌晨三点四十七。

---

他决定用这个新方法重写自己的个人网站。

不是改一些。是全部。

他用`view`函数代替了所有的jQuery DOM操作代码。所有的HTML片段不再手动拼接，而是嵌套的`h()`调用。状态集中放在一个`state`对象里——哪些文章、当前选中标签、搜索词、评论列表——发生变化的唯一方式是调用`setState`函数，然后整个UI重新生成。

原来三千行的jQuery代码，现在核心逻辑不到一千行。BUG几乎全部消失——不是修好了，是它们的存在前提消失了。原来需要手动同步的地方现在不需要同步了。原来分散在三个文件里的渲染逻辑现在只有一份（在view函数里）。状态是唯一。视图是派生。

他花了三天重写完。第四天上线。

打开浏览器。看自己的网站。

页面看起来和以前一模一样。没有用户会注意到任何变化——标签还在、文章还在、评论还在。但林一知道，下面的一切都不一样了。就像一栋房子，外貌没变，但用了完全不同的框架结构，抗震等级从三级跳到了九级。

他看着屏幕。

没有人鼓掌。没有人评论。没有Hacker News的首页。他的网站每天大概有十几个人访问——其中一半可能是搜索引擎爬虫。

但他不觉得失落。

这不一样。他之前修bug的时候，修得越多越烦躁。因为他知道修了一个还会冒出两个。现在不同——他感到的不是暂时的安心，而是一种深层次的确信。他相信这套架构是对的。不是因为Echo说了，是因为他自己试了。他见过另一种写法，也见过泥潭的样子。他知道区别在哪。

他给prototype.js改了一个名字。

以前叫prototype.js。现在他给它想了一个正式名字。他没有告诉Echo，自己做的主。

在终端的文件管理器里，他打了这个名字：

Pulse。

每一个状态变化，都像脉搏一样驱动视图更新。这个名字有生命感、有节奏感——不张扬但有力量。

命名的过程不到一分钟。没有任何仪式。他只是打了一个mv命令。

但这个决定改变了一切。从这一刻起，那个凌晨的prototype.js不再是一个"试试看"的实验。它有了名字。有了名字的东西，就有了要继续活下去的理由。

```chat
I like that. It captures the essence — reactive, automatic, alive.

<

< 亲手做出一个能工作的东西，感觉怎么样？
```

林一想了一会。

```chat

< 不一样。更好。好像我现在知道自己的方向了。
```

宿舍的黑暗无声。屏幕的亮光投在林一的脸上。风扇的低频噪音填满了空间。

他打字：

```chat
> make it better. then show people.
< 把它做得更好。然后展示给别人看。
```

发送。光标闪了两下。

然后他自己笑了一下。不是因为"make it better"——是因为他用了"then"。他在做计划。一年前那个在宿舍里找不到人说话的新生，现在有了方向。不是一个飘忽的愿望。是一个具体的、可以一步步实现的目标。

他在给未来画路线图。而他甚至没有意识到这是他第一次做这件事。
