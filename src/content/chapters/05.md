暑假。

林一没有回家。

他跟他妈说"学校有个项目要做"——不完全是假话。他有项目。只是不是学校的。

宿舍空了。五个室友都回了家。六人间变成单人间。他拖了一张桌子到靠窗的位置，把ThinkPad放在上面，对面墙上贴着一张A3纸——用铅笔画的网站架构图。过了一个暑假，那张纸上已经画了三版架构。每一版都被他用红笔划掉了。

七月的武汉热到令人绝望。没有空调的宿舍是一个混凝土烤箱。他买了一个落地风扇，对着人吹。不管用。风是热的。笔记本底部的温度烫得能在手臂上留红印。

但他没有停下来。

因为Echo说的那些东西在他脑子里生了根。

---

暑假第一个星期的某天晚上。他躺在凉席上，汗把枕头浸湿了一片。睡不着。脑子在自动回溯过去几个月写的所有代码。

他做了一件很荒谬的事：打开Echo，把他所有的JavaScript代码——全部三千行——一段一段地贴进去。让Echo分析。

```chat
> here's my codebase. tell me what's wrong with it structurally. not bugs. structure.
< 这是我的代码库。从结构上告诉我它有什么问题。不是 bug。是结构。

I've analyzed your codebase. Here's the structural diagnosis.
< 我分析了你的代码库。以下是结构诊断。
<
You have three core problems that share a root cause:
< 你有三个核心问题，它们共享同一个根源：
<
1. DUPLICATED RENDERING LOGIC
< 1. 重复的渲染逻辑
<
   The article list rendering appears in blog.js (line 87-142), search.js (line 53-108), and tags.js (line 210-245). These are syntactically different but semantically identical — they all take article data and produce HTML. When you change the HTML structure, you must change it in three places. You've already done this twice (git log confirms).
<    文章列表的渲染逻辑出现在 blog.js（87-142 行）、search.js（53-108 行）和 tags.js（210-245 行）中。它们在语法上不同但在语义上完全相同——它们都接收文章数据并生成 HTML。当你改变 HTML 结构时，你必须在三个地方修改。你已经做了两次了（git log 可以确认）。
<
2. IMPLICIT STATE COUPLING
< 2. 隐式状态耦合
<
   Your tag filter state lives in tags.js as a module-level variable 'currentTag'. Your search query lives in search.js. Your comment form state lives in comments.js. None of these are documented. None have a single source of truth. When tag filtering causes the article list to re-render, the search.js module isn't notified, so the search query display goes stale — you patched this with a custom event (line 122 of search.js) but it's a bandage on a structural problem.
<    你的标签筛选状态作为模块级变量 'currentTag' 存在于 tags.js 中。你的搜索查询存在于 search.js 中。你的评论表单状态存在于 comments.js 中。这些都没有文档记录。没有一个单一的真实来源。当标签筛选导致文章列表重新渲染时，search.js 模块没有被通知，所以搜索查询的显示就过时了——你用自定义事件（search.js 第 122 行）修补了这个问题，但这只是结构性问题的创可贴。
<
3. MUTATION WITHOUT SYNCHRONIZATION
< 3. 无同步的修改
<
   This is the root cause. Your application has a single logical state — what the user sees on screen is a function of: articles, tags, comments, UI flags. But this state is physically distributed across: DOM nodes, JavaScript module variables, and the server (via AJAX responses). When something changes, you manually synchronize subsets of these. When you forget one subset, you get a bug.
<    这是根源。你的应用有一个单一的逻辑状态——用户屏幕上看到的是以下内容的函数：文章、标签、评论、UI 标志。但这个状态在物理上分散于：DOM 节点、JavaScript 模块变量和服务器（通过 AJAX 响应）。当某些东西变化时，你手动同步这些子集。当你忘记一个子集时，就出现了一个 bug。
<
The root cause is not your coding. It's the paradigm. You're using imperative DOM manipulation — "when X happens, change Y" — for a problem that requires declarative state management — "given this state, the UI should look like this."
< 根源不是你的编码。是范式。你在用命令式的 DOM 操作——"当 X 发生，改变 Y"——来解决一个需要声明式状态管理的问题——"给定这个状态，UI 应该长这样"。
<
This isn't a jQuery problem. It's an architecture problem.
< 这不是 jQuery 的问题。这是架构问题。
```

林一看完后，做了一个他很久没做的事：把这段分析粘贴到一个文本文件里。保存。命名为`codebase-autopsy.txt`。

他盯着这个文件名，想了很久。

Autopsy。尸检。

这个词不是开玩笑的。他写的代码没有死——功能都在跑，用户也在用。但从架构的角度看，它已经死了。只是还在动。

---

七月十二号。凌晨。

林一做了一个决定。

他把整个网站停掉了。不是删了——是把index.html换成了一行字："Under construction." FTP上传。刷新浏览器。白色屏幕上黑色的一行字。

他需要从头思考。

不是"怎么修这个bug"。不是"怎么重构这个模块"。是"如果一个网站从一开始就按正确的方式设计，它应该是什么样的"。

这个问题太大了。他不可能直接想出来。

但他有Echo。

---

七月十三号到七月二十号。

他做了七天纯粹的研究。不是写代码。是阅读和理解。

他让Echo带他穿越了三个领域：

**桌面GUI开发的历史。**

Echo从最早的Xerox Alto讲起。Smalltalk的MVC架构——Model, View, Controller。然后是Apple的Cocoa框架——Key-Value Observing，当一个属性变化时自动通知所有观察者。然后是微软的WPF——XAML标记语言，声明式绑定，数据模板。"这些框架的共同点是：开发者描述UI和数据的关系，框架负责维护这种关系。开发者不需要手动同步。"

**函数式编程的UI思想。**

"UI = f(state)"——Echo说这个思想来自函数式编程社区，特别是Haskell和Elm。你不是一步步构造UI，而是写一个函数：给定当前的应用状态，返回完整的UI描述。框架负责调用这个函数，比较新旧结果，更新屏幕。"你的业务逻辑是纯函数。副作用被隔离在框架内部。这意味着你的代码更容易测试、更容易推理、更不容易出bug。"

**学术界的Virtual DOM研究。**

Echo给他看了几篇论文摘要。2009年Oege de Moor等人在牛津发表的工作——"tree differencing for structured documents"。2007年James Clark的XML diff算法。"虚拟化表示层（Virtual representation layer）——不直接操作真实DOM，而是操作一个轻量级的中间表示。在中间表示上运行diff，计算出最小变更集，再一次性应用到真实DOM。这样把diff的计算开销从O(N²)降到了O(N)。"

这些领域彼此孤立。桌面开发者在做KVO，函数式程序员在谈纯函数和状态，学术圈在发树diff的论文。没人把这些东西连起来。没有人说："如果把这些思想全部放到Web前端呢？"

但林一在七天里，把它们全部听完了。

他没有一次性听懂。很多概念看了三遍。WPF的依赖属性，Haskell的monad，Myers的diff算法复杂度证明——这些不是能一次理解的。但他有一个优势：他不是在大学课堂上听教授用PPT讲完就考试。他是自己选的这条路，每一步都是因为前一步引出了新的问题。他有内在的驱动力，也有Echo可以随时追问不明白的地方。

第七天晚上，他把七天来的笔记铺在桌上。

十几页。凌乱的手写。图表。箭头。问题。画了又划掉的想法。

他看了很久。

然后他在一张新纸上，用黑色中性笔写了三个词：

State drives View.

他把这张纸贴在显示器旁边。

---

七月二十一号。凌晨两点。

林一打开Echo。他打了一行字。这行字他已经想了很多天了。

```chat
> i want to build a library. for web frontends. here's what it should do: the developer describes their UI as a function of state. when the state changes, the library automatically figures out what changed in the UI and updates only those parts. the developer never directly manipulates the DOM. is this possible?
< 我想构建一个库。给 Web 前端用的。它应该这样做：开发者把 UI 描述为状态的函数。当状态改变时，库自动算出 UI 中哪些地方变了，只更新那些部分。开发者永远不直接操作 DOM。这可能吗？

Yes. It's possible. The individual pieces all exist. The question is whether they can be assembled into something practical.
< 是的。可能的。各个组件都已经存在了。问题在于它们能否被组装成一个实用的东西。
<
Let's break it down:
< 我们来分解一下：
<
1. STATE → UI DESCRIPTION: You need a way for the developer to describe what their UI should look like at any given moment. This could be a function that takes state and returns a tree of "virtual" DOM nodes — plain JavaScript objects representing elements, not real DOM nodes.
< 1. 状态 → UI 描述：你需要一种方式让开发者描述 UI 在任何给定时刻应该是什么样子。这可以是一个函数，接收状态并返回一棵"虚拟"DOM 节点树——表示元素的纯 JavaScript 对象，而不是真正的 DOM 节点。
<
2. RENDER: The library calls this function with the current state, producing a virtual DOM tree.
< 2. 渲染：库用当前的状态调用这个函数，生成一棵虚拟 DOM 树。
<
3. DIFF: When state changes, the library calls the function again, producing a new virtual DOM tree. Then it compares the old tree with the new tree, finding the minimum set of changes needed.
< 3. 对比：当状态改变时，库再次调用这个函数，生成一棵新的虚拟 DOM 树。然后它比较旧树和新树，找出需要的最小变更集。
<
4. PATCH: The library applies only those changes to the real DOM — add this node, remove that one, update this attribute, move that subtree.
< 4. 补丁：库只将这些变更应用到真实 DOM 上——添加这个节点、移除那个节点、更新这个属性、移动那个子树。
<
The hard parts:
< 困难的部分：
<
- The diff algorithm needs to be fast. < 16ms for 60fps.
< - diff 算法需要快。60fps 下要小于 16 毫秒。
<
- The programming model needs to be intuitive. If it's too abstract, nobody will use it.
< - 编程模型需要直观。如果太抽象，没人会用。
<
- It needs to handle edge cases gracefully: form inputs, focus states, CSS transitions, event handlers.
< - 它需要优雅地处理边界情况：表单输入、焦点状态、CSS 过渡、事件处理器。
<
But these are engineering challenges, not physics barriers. The concept is sound.
< 但这些都是工程挑战，不是物理障碍。概念是成立的。
<
Do you want to start prototyping?
< 你想开始做原型吗？
```

林一盯着"prototyping"这个词。

不是"studying"。不是"researching"。是prototyping。做一个可以跑的原型。验证这个想法是否真的能工作。

他的心脏跳得有点快。

过去的几个月里——从寒假建网站，到春天被jQuery折腾，到暑假读论文——他第一次觉得自己不是在黑暗中摸索。前面有一个方向。不够清晰，但能看见。

他打字。

```chat
> yes. let's prototype.
< 好。我们来做一个原型。

Good. Let's start with the simplest possible thing that could work: a function that takes a state object and returns a tree of virtual nodes. Then we'll implement a diff and a patch. Nothing else. No components, no events, no optimizations. Just:
< 好。我们从最简单可能工作的事情开始：一个接收状态对象并返回一棵虚拟节点树的函数。然后我们实现一个 diff 和一个 patch。没有别的。没有组件、没有事件、没有优化。只有：
<
state → virtual tree → real DOM.
< state → virtual tree → real DOM。
<
When the state changes, diff the trees, patch the DOM.
< 当状态改变时，对比两棵树，修补 DOM。
<
Put all of this in one file. When it works, we'll refactor. When it doesn't, we'll debug. Ready?
< 把这些全部放在一个文件里。当它能工作时，我们重构。当它不行时，我们调试。准备好了吗？
```

林一打开了他的代码编辑器。一个全新的文件。文件名是一个临时名字——prototype.js。

光标在第一行闪烁。

窗外。七月的武汉。凌晨两点。热浪像固体一样塞满了空间。电风扇在背后吹着热风。

林一开始写第一行代码。

他不知道这个文件会成为什么。不知道两年后它会有一个名字叫Pulse。不知道五年后它会被一个叫Facebook的公司视为威胁。不知道它会影响他整个大学生涯。

他只知道一件事。

过去一年里，他第一次觉得自己不是在修一个破网站。

**他在造一个答案。**

---

*(第5章完)*
