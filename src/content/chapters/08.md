大一下学期。二月返校。

林一坐在同样的宿舍、同样的3号床。室友们一个接一个回来——1号床带了家里的腊肉，给每个人分了一块。5号床换了一部新手机，HTC的，电容屏，手指划起来比电阻屏顺畅十倍。6号床一进门就打开电脑，DOTA的更新包已经下好了。

一切和上学期一模一样。但又不一样了。

不一样的是林一的电脑里多了一个叫Pulse的目录。它安静地躺在`~/projects/pulse/`下面，像一个休眠的种子。

---

开学第一周。课表依然稀疏。高数下、英语下、C语言下——还是C语言。林一翻了一下教学计划，这个学期讲指针。指针，整个C语言课程里最难也是最核心的部分。上学期期末的时候他已经把指针倒背如流了，连函数指针和指针数组的区别都分得清清楚楚。这门课对他已经毫无意义。但他还是得坐在教室里。因为点名。

他在C语言课上做的事情和上学期一样：坐在最后一排，开着ThinkPad。不同的是，上学期他在学C，这学期他在打磨Pulse。

他设了一个目标：在四月之前，把Pulse打磨到可以给人看的程度。

---

打磨的第一件事：API设计。

他现在的API能用，但不好看。`h('div', {class: 'container'}, [...])` 对于习惯了HTML的开发者来说不够直观。他需要一个更容易接受的入口。

他和Echo讨论了很久。

```plaintext
> the h() function is too alien. web developers are used to writing HTML, not function calls.
```

```plaintext
A few approaches:

1. JSX-like syntax: embed XML-like markup directly in JavaScript. `<div class="container"><p>Hello</p></div>` inside JavaScript code. This requires a build step — a compiler that transforms markup into h() calls. Powerful, but adds tooling complexity.

2. Template literals: use backtick strings with interpolation. `html\`<div class="container"><p>${name}</p></div>\``. Simpler, no build step, but harder to do static analysis on.

3. Keep h() and let developers get used to it. If the value proposition is strong enough, the syntax is surmountable. jQuery's `$()` was also "weird syntax" when it first appeared.

Trade-off: approach 1 is most natural for developers but requires building a compiler. Approach 2 is pragmatic but limited. Approach 3 is simplest but has adoption friction.

What's your priority right now — making it easy to adopt, or keeping it simple to maintain?
```

林一选了第三条路。暂时。他需要先把框架本身打磨好，再考虑降低门槛的问题。而且——他看了看2011年早期的前端社区——grunt刚出来，browserify还在襁褓里，webpack连概念都没有。在这个时候做一个JSX编译器，意味着他要单独写一个构建工具链。他现在没这个精力。

保持`h()`。把文档写清楚。

---

打磨的第二件事：组件API。

他最初的组件是一个函数——接收props，返回虚拟DOM树。足够简单。但不够强大。

实际使用中，他遇到了一些问题：

- 组件内部需要自己的状态，不能全部放在全局state里。
- 组件需要生命周期——挂载时做什么，更新时做什么，卸载时清理什么。
- 组件之间需要通信——父子简单，兄弟复杂。

他花了两周，和Echo一起设计了新的组件API：

```javascript
Pulse.component({
  name: 'Counter',
  state: function() {
    return { count: 0 };
  },
  render: function(state, props) {
    return h('div', {}, [
      h('button', {onclick: '<increment>'}, ['+']),
      h('span', {}, [state.count]),
      h('button', {onclick: '<decrement>'}, ['-'])
    ]);
  },
  increment: function(state) {
    state.count++;
  },
  decrement: function(state) {
    state.count--;
  }
});
```

每个组件有自己的state，互不干扰。render函数只依赖自己的state和传入的props。事件处理用字符串映射——`'<increment>'`——框架在内部解析和绑定。这避免了每次渲染创建新的函数对象。

Echo对这个设计给他的反馈：

```plaintext
The `<event>` string mapping is elegant — it avoids creating new function objects on every render. But it also means event handlers are resolved by name, which can be confusing at scale. Consider also supporting direct function references for components that don't need the optimization.

The state-as-mutable-object pattern is pragmatic but dangerous. If a developer mutates state without going through the framework, the view won't update. Consider a `setState` API instead — make mutation explicit and traceable.

These are refinements, not flaws. The foundation is solid.
```

林一读了这些反馈。提笔记下。

他决定两件事都要做——支持事件名映射和直接函数引用，加`setState`方法。但他没有立刻改。他在改之前做了一件事：把Echo的反馈抄到了Pulse的TODO文件里。

这个习惯是Echo教他的：**在修改之前，先记录为什么要修改。** 将来回顾的时候，你才知道一个设计决策是怎么形成的。

---

打磨的第三件事：性能。

他之前测过——20个节点的diff是0.8ms。现在Pulse的虚拟DOM树有更复杂的节点结构（组件、事件绑定、样式属性），他需要重新评估。

他写了一个benchmark suite。用一个有100个组件的页面场景——每个组件有嵌套的div、span、button，总共约500个虚拟DOM节点。模拟一次典型的state更新——只改一个叶子节点的文本。

结果：diff耗时3.2ms。

够快了。但Echo指出："500个节点就3.2ms？1000个呢？2000个呢？你需要更智能的跳过策略。"

他加了一个优化：`shouldUpdate`。组件可以在更新前检查——如果新旧props和state都相同，跳过整个子树的diff。

加上之后，同样的场景：0.6ms。因为只有那一个变化的叶子节点触发了更新。其余499个节点全部跳过。

他又跑了一遍。0.5ms。

他盯着这个数字，感到一阵满足。不是成功的兴奋——是工程师的满足。像把一块毛边磨平，直到手指摸上去光滑。

---

三月底。春雨连绵。

林一坐在图书馆二楼靠窗的单人座。面前是Pulse的文档——不是给用户看的，是给他自己看的。他在整理Pulse的API参考手册，把每一个公开的函数和方法写成结构化的说明。他知道将来如果开源，这些文档会直接变成用户文档的第一稿。

春雨打在窗户上，声音细密而均匀。图书馆里人不多——不是考试季，阅览室大半是空的。偶尔有人从书架间走过，脚步声在瓷砖地面上显得很轻。

他写完了最后一行文档。靠在椅背上，看着窗外灰蒙蒙的天空。

Pulse现在是什么状态？

- 核心虚拟DOM引擎：稳定。经过上百次测试，没有已知bug。
- 组件系统：完整。有独立状态、生命周期、嵌套、通信。
- 状态管理：清晰。`setState`触发视图更新，`shouldUpdate`优化性能。
- 事件系统：稳健。合成事件、委托、名映射和函数引用双模式。
- 文档：草稿完成。API参考、快速入门、最佳实践。
- 测试：有。覆盖核心路径。但不够全面——他自己写的测试，覆盖面有盲区。

总计约2500行。比寒假时的1800行多了700行——不是框架变臃肿了，是功能更完整了。组件系统从最初的简单函数变成了真正的组件树管理器。事件系统从简单的属性绑定变成了合成事件层。

这个框架是"可用的"。不是"可以跑通"——是"一个有一定前端经验的开发者，读过文档之后，可以用它从零构建一个真实的网站"。

但他知道还有差距。Pulse可以处理他个人网站的那种复杂度——几十个页面、评论、标签、搜索。但能不能处理更大的东西？他不知道。他没有更大的项目可以测试。

他把文档关掉，打开了课程表。

下个月有一门课叫"数据结构"。任课老师叫周默。

他还没有见过这个人。
