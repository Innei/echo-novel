二月。开学前一周。

Pulse的star数安静地爬过了三百。不是爆款，但也不是死寂——每天三五个新增，偶尔一天十几个。issue区保持着每天两三条的节奏。赵恺回复了一半——英文比寒假时流利了不少。林一回复另一半。

然后来了一个issue。

标题："Support for two-way data binding"

内容写得很长。一个叫"frontend_dev_cn"的用户发帖。他说他试用了Pulse之后很喜欢组件系统的设计，但觉得单向数据流在表单场景里太麻烦了。"你每次输入都要写一个onChange事件来更新state——这太啰嗦了。能不能像Angular一样直接双向绑定？`<input data-bind="name">`，输入框变了，name自己变。"

语气礼貌。但林一看到了问题。

他回复了一长段，解释为什么Pulse选择单向数据流——"单向数据让状态变化可预测。双向绑定在复杂页面里会让数据流向变得不可追踪——你不知道是哪个组件改了数据，也不知道改了几次。单向虽然多了几行代码，但调试的时候能省几个小时。"

回复发完。林一以为这件事就结束了——解释清楚了，对方会接受。但第二天那个人又回了一大段——"你说的对，但我做的后台管理项目有几十个表单。每个输入都写一遍onChange，开发效率太低了。能不能至少加一个快捷方式？"语气还是礼貌的，但这次举了具体的业务场景。

林一开始感到一种微妙的不适。不是因为这个人的需求不合理——表单场景确实有大量重复输入，他的观点有道理。而是因为这件事的本质——他不是在辩论，他是在被游说。对方希望他改变设计，而他想保持设计。

他问Echo。

```chat
> someone keeps asking for two-way binding. i explained why i chose one-way. he's not wrong about the problem, but i don't think two-way is the right solution. do i compromise?
< 有人一直要求双向绑定。我解释了为什么选单向。他对问题的描述没错，但我不认为双向是正确的方案。我该妥协吗？

This is a classic open source governance challenge. The user has identified a real UX problem — excessive boilerplate for form-heavy applications. Your diagnosis is correct — two-way binding creates unpredictable data flow at scale. But you can't simply dismiss the problem.
< 这是经典的开源治理难题。用户发现了一个真实的用户体验问题——表单密集的应用中样板代码过多。你的判断是正确的——双向绑定在大规模下会导致不可预测的数据流。但你不能简单地驳回这个问题。

The responsible thing is to acknowledge the problem while holding your design line. Consider this framing:
< 负责任的做法是承认问题同时守住设计底线。考虑这样的表述方式：

"Two-way binding isn't the right fit for Pulse's architecture. But the problem you're describing — excessive boilerplate for form inputs — is real. I'm tracking this in [issue #X]. The solution might be something like a form helper that generates the onChange boilerplate automatically, or a plugin system that lets users build their own form helpers. But whatever the solution, it needs to preserve predictable data flow."
< "双向绑定不适合Pulse的架构。但你描述的问题——表单输入的样板代码过多——是真实存在的。我在[issue #X]中跟踪这个问题。解决方案可能是一个表单辅助工具，自动生成onChange样板代码，或者一个插件系统让用户构建自己的表单辅助工具。但无论方案是什么，都需要保持可预测的数据流。"

This validates the user's pain point, protects your architecture, and opens the door to a solution that doesn't compromise either.
< 这既认可了用户的痛点，保护了你的架构，又为不损害任何一方的解决方案打开了门。

Open source leadership isn't about winning arguments. It's about finding paths where everyone wins.
< 开源领导力不是赢得争论。是找到让所有人都赢的路径。
```

林一读了两遍。然后把Echo建议的方案写成了回复。

发完之后，frontend_dev_cn回复了："OK，我理解了你的立场。期待form helper的方案。"

issue close。

林一靠回椅子上。松了一口气。但同时也感到一种疲惫——不是因为这一次对话长，是因为他知道下一次类似的对话还会来。会有下一个想加的人，下一个需要被说服的人。这不是一个bug——这是开源维护的一部分。

---

三月。又一个issue。

标题："Remove h() function, it's ugly"

开门见山。"我不明白为什么要用函数调用来描述HTML。这太丑了。jQuery里面我可以直接写HTML字符串，Pulse里要变成一大堆嵌套的h()调用。阅读性极差。"

林一盯着屏幕。呼吸变浅——不是因为被批评，而是反驳的话已经到了喉咙口。`h()`有存在的理由——类型安全、编译时检查、避免XSS漏洞、避免字符串拼接的性能问题。他在脑子里过了这些问题。然后想到Echo常说的一句话："每次冲突都是设计决策的复现。"不是防御。是回顾自己为什么要做这个选择。

但还有一个更深的问题：这些issue让他把夜晚分成了两半——一半回答陌生人，一半才能安静写代码。而前一半增长的速度比后一半快。

Echo的回复浮在屏幕上：

```chat
This is the tension at the heart of open source. Every contribution requires maintenance — not just code maintenance, but social maintenance. Answering questions, managing expectations, saying no gracefully.
< 这就是开源核心的矛盾。每一个贡献都需要维护——不仅仅是代码维护，还有社交维护。回答问题、管理期望、优雅地说不。

Some people burn out from this. You need to find a sustainable pace — and you need help. Have you considered bringing in more collaborators to share the load?
< 有的人会因此倦怠。你需要找到一个可持续的节奏——而且你需要帮助。你有没有考虑引入更多协作者来分担负担？
```

林一："I have Zhao Kai. But he can only handle simple issues."

```chat
Then you need someone who can handle complex issues — someone who understands Pulse's design philosophy deeply enough to answer architecture questions without your involvement.
< 那你就需要一个能处理复杂问题的人——一个深入理解Pulse设计理念、能在不涉及你的情况下回答架构问题的人。

Two potential paths:
< 两条可能的路径：

1. Identify active community members who consistently give good answers and offer them commit access or "maintainer" roles. This is how many open source projects scale.
< 1. 识别社区中持续给出优质回答的活跃成员，给他们commit权限或"维护者"角色。很多开源项目就是这样扩展的。

2. Write more documentation. Many support questions arise because the docs are incomplete or unclear. A well-written design principles document — explaining *why* Pulse makes the choices it does — can preemptively answer a significant percentage of issues.
< 2. 写更多文档。很多支持请求是因为文档不完整或不清晰而产生的。一份写好的设计原则文档——解释Pulse*为什么*做这些选择——可以预先回答相当比例的issue。

Both paths require upfront investment of time. Both pay off by reducing your ongoing maintenance burden.
< 两条路都需要预先投入时间。两条路都能通过减少你的持续维护负担来回报。

Which one feels more feasible right now?
< 现在哪条路你觉得更可行？
```

"文档。"林一回复。

"Good choice. Start with a DESIGN.md file. Not API documentation — a design philosophy document. 'Why h()? Why one-way data flow? Why virtual DOM?' Write it once, link to it forever."

---

四月中旬。他写完了DESIGN.md。

三千多字。解释了Pulse的每一个核心设计决策：为什么用`h()`而不是HTML字符串、为什么选择单向数据流、虚拟DOM为什么比直接操作DOM更安全、为什么key是必须的、为什么不做"全栈框架"而专注于视图层。

Echo帮他审了语法和逻辑。赵恺帮他调了排版。然后林一把它提交到repo里，放在了README的"了解更多"部分。

第二天。之前抱怨"h()太丑"的那个用户在issue下面回了一句：

"Didn't see the DESIGN.md when I opened the issue. Makes sense now. Thanks."

林一看完这句。把issue关了。

一个字也没回。

不是因为生气。是因为他意识到——很多争议不是观点冲突，是信息缺失。对方不知道他为什么做某个选择。不是故意找茬。是默认假设"你没想过"。

DESIGN.md的作用不是说服所有人。是让那些质疑的人看到——他想过。每一个选择都有理由。可以不同意，但不能说他没想过。

---

五月的一个晚上。他打开issue列表，发现了一个不寻常的标题。

"We're using Pulse in production and loving it"

邮件来自一个叫"techlead_jp"的账号。正文是英文。语气介于兴奋和郑重之间。

> Hi，我们是一个日本的初创团队。三个月前开始在我们的管理后台中用Pulse替换jQuery。目前大约有30个组件在生产环境中运行。迁移过程中最大的收益不是性能——是重构的可维护性。因为组件的状态和视图是显式关联的，改一个功能不需要追踪所有影响到的地方。
>
> 我们发现了几个bug——主要是IE兼容性和事件系统在大量组件下的性能退化。已经提交了PR修复这两处，希望你能review。

```

林一读了三遍。

有人在使用Pulse。不是"我试了试demo"——是"一个月前替换了jQuery，现在三十个组件在生产环境跑"。而且他们提了PR。不是只报告bug——是修好了bug，然后把代码送回来给他。

他打开了那个PR。代码干净。注释清晰。commit message写的规范。他review了大约二十分钟，留下两条建议。然后点了merge。

这个PR被合并的那一刻，林一感到一种非常陌生的感觉。不是骄傲——是某种更冷静的东西。他写的东西不只是"被看到了"——是在被使用。在真实的任务里，在另一个国家，被他不认识的人。

Pulse不再只是他的了。它开始属于使用它的人。

```chat
> someone in japan is using pulse in production. they submitted a bug fix pr.
< 日本有人在生产环境中用Pulse。他们提交了一个修bug的PR。

That's a milestone. Open source projects cross this threshold when they go from "interesting experiment" to "something people depend on."
< 这是一个里程碑。开源项目在从"有趣的实验"变成"人们依赖的东西"时，就会跨过这道门槛。

How does it feel?
< 感觉怎么样？

> strange. heavy. like i have responsibility now.
< 奇怪。沉重。好像我现在有了责任。

You do. When people depend on your code in production, breaking changes aren't just inconvenient — they cost real time and money. This is the weight of infrastructure.
< 你确实有。当人们在生产环境中依赖你的代码时，破坏性变更不只是不方便——它们会浪费真实的时间和金钱。这就是基础设施的重量。

But it's also the proof. You didn't just build something that works. You built something that someone else decided was worth betting on. For a solo developer working from a dorm room, that's extraordinary.
< 但这也是证明。你不只是做了一个能用的东西。你做的东西，别人决定值得押注在上面。对于一个在宿舍里独自开发的开发者来说，这是非凡的。
```

林一靠在椅子上。窗外夜色沉静。Echo的"extraordinary"在屏幕上闪。

他从来没有觉得自己做的东西"extraordinary"。他只是想解决自己的问题——网站太乱，DOM操作太烦。然后一步步把它改进。然后被人看到。被人用了。被一个在日本的团队放到了生产环境里。

不是因为有远见——而是每一步都只关注"下一步"。

---

但重量也是真实的。

那个日本团队只是第一批。之后还会有更多用户，更多需求，更多需要他说"可以"或"不可以"的请求。他没有团队——除了赵恺，能扛得住的只有他一个。周默可以给建议，但不是维护者。Echo可以写代码和文档，但不是那个"说不"的人。

他不知道自己能不能撑住。但至少现在，他知道了重量长什么样。不是概念上的"压力"——是每天的issue，每封邮件，每个PR。是具体的东西。不是一个模糊的担忧。

能用具体来对付的东西，总比模糊的好。

他回到键盘前。打开了issue列表。还有五个没看。

---

*(第14章完)*
