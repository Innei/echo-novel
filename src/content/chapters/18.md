陆辰回了邮件。只用了十五分钟。

> 同意。"最笨实现"这个想法很好。我加一条：两个框架都用同一个标准——同一套测试数据、同一个DOM容器、同一个计时方式。不是谁优化得好，是谁的默认路径更短。
>
> 下周GitHub discussion见。

林一看完这封邮件。短短几行。没有多余的客套，没有"很高兴认识你"——直接讨论技术。这和他预想的不一样。他以为和陆辰的第一次交流会是某种"惺惺相惜"——但陆辰的方式更像是"好的我们开始吧"。不冷不热，不近不远。像他自己和Echo说话的方式。

不是冷漠。是效率。

---

公开benchmark在GitHub discussion区发布之后，前端技术社区有了反应。

Hacker News上的讨论帖进了首页。有人说"这是前端领域的两个开源框架在用工程数据讨论一个设计问题——在任何一个领域这都是健康的现象"。有人调侃"所以你们什么时候开打"——这个人只看了标题。但更多是认真的——有人在等数据对比，有人在讨论测试用例的公平性。

林一花了两天准备Pulse的benchmark方案。他从多个维度覆盖：初始渲染、增量更新、大量数据、频繁更新、深层嵌套。每一个测试用例都公开在GitHub上——代码、测试步骤、预期结果。markus帮他审了一遍测试用例的公平性——"你用Pulse的默认路径和Axiom的默认路径对比，这才是对等的"——做了几处关键修正。佐藤帮他做了数据可视化——"如果你想要Hacker News上的人看，你需要的不是文字，是表格和走势图。"

发布之前，林一打开Echo。光标在闪。他停了一下。不是问策略——是确认一件事。

```plaintext
> is it right to make this public? the benchmark.
```

```plaintext
Yes. Making performance comparisons public is a sign of maturity in an open source project. It says: "I'm confident enough in my work to let others measure it." It also signals to users that you care about real-world performance, not just marketing claims.

One caution: benchmarks are partial truths. They measure specific things under specific conditions. A framework can win every benchmark and still be worse for certain use cases. Make sure the discussion thread includes context about what the benchmarks *don't* measure — developer experience, ecosystem, learning curve, documentation quality.

And be prepared for the possibility that Axiom wins some categories. If that happens, acknowledge it gracefully. The goal isn't to "beat" Axiom — it's to advance the understanding of declarative UI. If Axiom wins on compilation speed, Pulse users benefit because now you know what to optimize next. That's not losing. That's learning in public.
```

Echo停了一下。光标闪了两下。

```plaintext
And Lin Yi — you're ready for this. Not because the code is perfect. Because you understand that public engineering isn't about winning. It's about building something worth measuring.
```

林一看着最后一行。关闭终端。发布了benchmark。

---

陆辰用了两天。他的方案和Pulse不同——不是复制了Pulse的测试用例，而是独立设计了一套新的。然后他把两套汇总到一个GitHub repo里——取名`declarative-ui-benchmarks`。

然后他说："我们各自跑对方的benchmark。不是在自己的机器上——在同一个CI环境里。"

林一："Travis CI？"

陆辰："Travis CI。"

于是两个人在GitHub上建了一个公开的CI pipeline。每次push，Travis CI自动跑两套测试——Pulse和Axiom各跑一遍对方的benchmark。

周三。第一次跑完的结果出来了。

在初始渲染方面：Pulse更快——Axiom的编译时模板需要额外的预处理开销，在实际冷启动中比Pulse的运行时方案慢了约15%。

在批量更新方面：Axiom更快——2000个节点的递归列表更新，Axiom平均比Pulse快约10%，得益于其编译后的代码路径更短。这是Axiom的核心优势——编译时优化把大量决策提前到了build阶段。

在深层嵌套组件方面：两者接近——都在50ms左右。

在频繁更新方面：Pulse在每16ms一次的更新压力下更稳定——波动小。Axiom出现了零星的帧超时（偶尔飙到18-20ms），可能与编译后的垃圾回收模式不同有关。

林一看着这些数字。然后他做了一件事——在讨论帖里发了一条评论。

> Benchmark results are in. Quick summary: Axiom wins on batch updates (compiled code path advantage), Pulse wins on initial render and update stability. Neither framework "beats" the other across the board — they make different trade-offs, and those trade-offs show up in the data exactly where you'd expect them. This is the outcome I was hoping for — not one framework winning, but the community getting concrete data about what matters for their use cases.
>
> @lukechen — impressive work on the compiled template path. I'd be interested in understanding the garbage collection patterns you're seeing. The occasional frame drops under rapid updates might be related to how compiled closures interact with the GC.

这条回复发完之后，几秒钟后。陆辰在下面回复了。

> @linyiyi — agreed on all counts. The GC issue is something I've been tracking — I'll open a separate issue in the benchmark repo with profiling data. And credit where it's due: your virtual DOM diff algorithm is cleaner than mine. I'd like to understand how you handle key-based reconciliation in edge cases (moved+modified nodes). If you're open to it, we could do a joint technical write-up comparing the two approaches?

林一看着"joint technical write-up"这几个词。不是他提的——是陆辰提的。那个天才——ACM金牌，985学生——主动提议他们合写一篇技术文章。

他回复："Yes. Let's do it."

然后他离开电脑。站在宿舍窗边。外面是冬夜。但这次路灯不只是橙色——远处教学楼的窗户亮着几点白光。不知道是谁在熬夜。但和他一样，那些灯也在醒着。

---

那篇合写的文章花了两周。

标题：《Declarative UI: Two Approaches to Virtual DOM》

内容对比了Pulse和Axiom的架构差异——运行时vs编译时、状态管理的单向vs响应式、diff算法的key-based vs heuristic。每一个对比都附了benchmark数据。没有结论说"谁更好"——而是说"这两种选择适合不同的场景"。

赵恺帮他们做了英文润色。markus审了技术准确性。佐藤用他的数据可视化工具做了图表——不是手画的，是自动从CI数据生成的。

发布当天。Hacker News首页。两个小时，一百多条讨论。Reddit的r/javascript版也进了首页。

有人评论说："This is what open source should look like. Two independent projects comparing architectures honestly, with data, in public. No drama. Just engineering."

林一和陆辰在评论区不断回复。有时是技术讨论，有时是补数据。大部分时候是他们互相补充——陆辰说"Pulse在X方面做得更好"，林一说"Axiom在Y方面做了我们没有的优化"。

有人的地方一定有站队——"Pulse赢了"、"Axiom赢了"这种评论时有出现。但更多的声音是："我两个都想试试。"、"Virtual DOM这个方向是对的。"、"希望两个框架都活下去。"

这些声音比谁赢谁输更重要。

---

文章发布后第三天。陆辰给林一发了一封私人邮件。

> 林一，
>
> 我看到你的GitHub repo下面有人问"你是怎么学的"——你从没直接回答过。我不追问这件事。
>
> 但我想让你知道一件事：我会继续做Axiom。不是因为我想赢Pulse——是因为方向是对的。而你是唯一在这片领域里我能真正讨论设计决策的人。不是因为我们都做虚拟DOM。是因为我们都理解为什么要做。
>
> 以后有什么设计难题——随时找我。不需要发到公开的discussion里。一封邮件就够了。
>
> 陆辰

林一看完这封邮件。靠回椅子上。窗外三月的风带着潮湿的气息。

他们不是朋友——至少现在不是。朋友需要时间、共同的经历、非技术领域的情感交流。他们只是两个在同一个问题上碰了头的人。但这种关系一样珍贵——不需要朋友的湿度，但能承载技术的重量。它更接近于"同行者"——你们朝同一个方向走，速度不完全一样，但足够近到可以互相喊一声"你脚底下有坑，向左边踩。"

他把邮件存档了。标签：陆辰。
